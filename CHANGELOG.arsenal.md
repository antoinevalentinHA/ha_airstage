# Arsenal fork changelog

Changes specific to the `antoinevalentinHA/ha_airstage` fork, branch `arsenal-stable`.
Upstream `CHANGELOG.md` remains untouched and is generated by semantic-release.

## [arsenal-2026.07.09] — 2026-07-09

### Fixed

- **fan speed no longer flaps back to the manufacturer `auto` (poll-after-set
  race):** every `async_set_*` / `async_turn_*` write used to call
  `coordinator.async_refresh()` immediately afterwards. The Airstage API is
  eventually consistent (`iot_class: local_polling`, 60 s local / 120 s cloud):
  for up to a poll interval after a write the unit keeps reporting its
  *previous* value. The immediate re-poll therefore read the stale value back —
  and for the fan speed that resurfaced the manufacturer `auto`. When an
  external automation reasserted the resolved speed on seeing `auto`, the two
  raced into a tight write → stale-read → rewrite loop (visible flapping,
  API hammering). Writes now perform an **optimistic local update** instead:
  the commanded value is patched into the coordinator's cached `parameters`
  (the source `AirstageAcEntity._ac` rebuilds its state from) and the
  coordinator's listeners are notified, so every entity reflects the target
  immediately with no network round-trip. The next *scheduled* poll — well past
  the unit's convergence window — reconciles with the device without an early
  stale read. Covers climate power/mode/fan/temperature/swing/preset and all
  switches (`entity.py`, `climate.py`, `switch.py`).

### Notes

- The firmware reset of the fan speed to `auto` on an operating-mode change
  (`cool`↔`dry`↔`heat`) is inherent to the Fujitsu unit and is not addressed
  here; it is still surfaced on the next poll (so an automation can re-correct
  it once), but it no longer compounds into flapping because the correction no
  longer triggers an immediate stale re-poll.

## [arsenal-2026.07.01] — 2026-07-01

### Fixed

- **no fake "off" on partial data:** `AirstageAC.hvac_mode` no longer returns
  `HVACMode.OFF` when `get_operating_mode()` raises `TypeError`/`ValueError`.
  That branch fires when the cached parameters are missing/`None` (e.g. a
  partial poll where `iu_onoff`/`iu_op_mode` were absent), and it made the
  climate entity report `off` while still `available` — an automation could
  then believe the unit was off while it was actually running. It now returns
  `None` (state "unknown"), which is honest and does not trip an "is it off?"
  check.
- **coordinator resilience on unexpected API responses:** Both the cloud and
  local `async_get` update methods now also convert non-`ApiError` leaks from
  `pyairstage` (`KeyError`/`ValueError`/`TypeError`, plus `OSError` on the
  cloud token file) into `UpdateFailed`. These are the paths that could
  otherwise surface as an unhandled "unexpected error" and, on the cloud auth
  path (token refresh returning an unexpected body, corrupt `token.json`,
  malformed JSON), turn a transient blip into a persistent failure. Treating
  them as `UpdateFailed` keeps the `DataUpdateCoordinator` polling on its
  interval so the entities recover on the next successful poll.

### Notes

- No availability is fabricated: a failed poll still marks the entities
  `unavailable`; the fix only ensures the failure is the documented transient
  path (retry + self-heal) instead of a swallowed exception or a lie about the
  runtime state.
- The underlying stale-token behavior lives in `pyairstage._read_token`
  (it trusts the locally-cached `expiresIn` and will keep returning a
  server-revoked token until it expires). A true fix belongs upstream; this
  change bounds the blast radius by keeping the coordinator retrying.

## [arsenal-2026.06.26] — 2026-06-26

### Fixed

- **quiet fan off restores manual speed:** Turning the Quiet switch off no
  longer forces the unit to `AUTO`. The last manual fan speed (`LOW`,
  `MEDIUM`, or `HIGH`) selected before Quiet was enabled is captured on
  turn-on and restored on turn-off. Non-manual speeds (e.g. `AUTO`, `QUIET`)
  are not restorable and fall back to `LOW`.

### Notes

- The previous speed is held in RAM only (`_previous_fan_speed`), so it falls
  back to `LOW` after an integration reload or Home Assistant restart.
- `get_fan_speed()` returns a `FanSpeedDescriptors` value while
  `set_fan_speed()` expects a `FanSpeed` value; the `_RESTORABLE_FAN_SPEEDS`
  map bridges the two and a `TypeError`/`ValueError` read is treated as "no
  restorable speed".

## [arsenal-2026.05.21] — 2026-05-21

### Changed

- **local polling interval 10 s → 60 s:** Raise `AIRSTAGE_SYNC_LOCAL_INTERVAL`
  (`const.py`) from `10` to `60`. This is the `update_interval` of the local
  `DataUpdateCoordinator`, so the integration now polls a locally-connected unit
  once a minute instead of every ten seconds. It cuts local request volume ~6×
  and widens the poll convergence window to 60 s — the "60 s local" figure the
  2026-07-09 optimistic-write entry cites as its premise. The two changes are
  complementary: with a 60 s window a naive poll-after-set would show a stale
  value for up to a full minute, which is precisely why writes were later made
  optimistic rather than re-polling immediately. The cloud interval
  (`AIRSTAGE_SYNC_INTERVAL`, 120 s) is unchanged.

## [arsenal-2026.05.20] — 2026-05-20

### Fixed

- **setup semantics:** Replace `ConfigEntryError` with `ConfigEntryNotReady` on
  both cloud and local branches of `async_setup_entry`. Transient device
  unavailability at boot is no longer logged as a permanent ERROR; Home
  Assistant now retries automatically with backoff per its documented
  convention for transient setup failures.
- **error message honesty:** Drop the misleading "Timeout while connecting"
  wording on the local branch. `pyairstage.ApiError` covers more than
  timeouts (`No valid response`, server-disconnect, payload errors), so the
  prior message was often wrong. New message names only the relevant
  identifiers (`device_id`, `ip_address`) and includes the underlying error.
- **log hygiene:** Stop dumping the full `entry.data` and `entry.options`
  dicts in the error message.
- **coordinator refresh semantics (base case):** On the coordinator's *refresh*
  path, the cloud and local `async_get` update methods now raise `UpdateFailed`
  (instead of `ConfigEntryNotReady`) when `pyairstage.ApiError` is raised. The
  two paths are now distinct: *setup* failures (first connection at boot) raise
  `ConfigEntryNotReady` so Home Assistant retries the entry setup; *refresh*
  failures raise `UpdateFailed` so the already-running `DataUpdateCoordinator`
  keeps polling on its interval and the entities recover on the next successful
  poll. This is the base case the 2026-07-01 entry later extends to non-`ApiError`
  leaks (`__init__.py`).

### Notes

- `async_config_entry_first_refresh()` is intentionally preserved on both
  branches. `entity.py` accesses `coordinator.data[ac_key]` at entity
  construction time (lines 55–56, 64), so a populated first refresh remains
  a hard prerequisite.
- No behavior change when the device is reachable.

## [arsenal-2026.05.19] — 2026-05-19

Founding stabilization commit for the Arsenal fork. Established the fork's
dependency baseline and hardened the entity read paths against partial /
missing device data.

### Changed

- **`pyairstage` dependency pinned to the 2.x line:** `manifest.json` requirement
  changed from `pyairstage>=3.2.0,<4` to `pyairstage>=2.4.1,<3` — a deliberate
  downgrade onto the 2.x lineage that the rest of the fork is validated against.
  Consequence: the fork does **not** rebase trivially onto any upstream change
  that depends on `pyairstage` 3.x; upstream bumps touching the 3.x API surface
  must be reconciled by hand.
- **manifest version `1.8.1` → `1.7.1`:** The fork advertises `1.7.1`, matching
  the 2.x-era integration rather than the upstream `1.8.1` release it was cut
  from.
- **`ApiLocal` call surface aligned with 2.x:** Drop the `use_https` and
  `timeout_seconds` keyword arguments from the local API construction
  (`__init__.py`). The `CONF_USE_HTTPS` constant (`const.py`), its config-flow
  field (`config_flow.py`), and its UI strings (`strings.json`,
  `translations/en.json`, `translations/nl.json`) are removed accordingly, and
  the `AIRSTAGE_LOCAL_TIMEOUT_SECONDS` constant is dropped — these parameters do
  not belong to the pinned 2.x `ApiLocal` signature.

### Fixed

- **defensive reads in `climate.py`:** `target_temperature`, `min_temp`,
  `max_temp`, `current_temperature`, `hvac_mode`, and `fan_mode` now guard the
  underlying `pyairstage` accessors against `TypeError`/`ValueError`/`KeyError`
  raised on partial or `None` cached parameters, falling back to constants
  (`COOL_MIN_TEMP`, `HEAT_MAX_TEMP`) or `None`/`current_temperature` instead of
  crashing the property. (`hvac_mode`'s fallback was `HVACMode.OFF` here; the
  2026-07-01 entry later corrects that to `None` so a partial poll no longer
  reads as a fake "off".)
- **defensive reads in `sensor.py`:** `AirstageTemp.native_value` wraps the
  indoor/outdoor temperature reads in `KeyError` guards and explicit `None`
  handling before constructing a `Decimal`.
- **defensive reads in `switch.py`:** the `is_on` properties of the energy-save,
  quiet, and power switches now guard against `TypeError`/`ValueError` and a
  `None` reading, returning `None` (unknown) instead of raising.

### Added

- **`.gitattributes`:** normalize line endings to LF for `*.py`, `*.json`,
  `*.md` (and `* text=auto eol=lf`) so the fork stays byte-stable across
  Windows/Linux checkouts.
- **`docs/ARSENAL_STABILISATION.md`:** narrative rationale for the fork.

### Notes

- Transitional setup error-handling introduced here (`PlatformNotReady` →
  `ConfigEntryError`) was superseded within a day by the 2026-05-20 setup and
  coordinator work (`ConfigEntryNotReady` for setup, `UpdateFailed` for refresh);
  see that entry for the current behavior.
- See `docs/ARSENAL_STABILISATION.md` for the "why" — the stabilization
  philosophy behind pinning to 2.x and hardening the read paths. This changelog
  is the factual "what"; that document is the rationale.
